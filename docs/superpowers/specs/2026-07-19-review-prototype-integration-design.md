# 审查原型界面整合设计

## 目标

将 `frontend/review/stitch_` 中的基础原型视觉体系整合到当前 Vue/Vite 项目，并补齐原型中的四步审查界面。现有智能问答、知识库、历史记录、收藏和详情管理功能继续保留，但只迁移视觉与布局，不改变其现有后端接口和业务语义。

新增的四步审查流程是独立的前端演示流程，不复用现有知识库或问答接口，也不新增后端审查能力。它需要具备完整的页面导航、选中状态、步骤切换和按钮反馈，使用本地演示数据表现原型效果。

## 设计原则

- 以原型的 `DocReview AI` 企业法务工作台作为全局视觉基准。
- 使用浅冷色应用背景、白色内容表面、深色文字和蓝色主操作色，保留原型的边框、4px/8px 圆角、步骤条和高信息密度布局。
- 视觉令牌集中在全局样式中，Element Plus 组件通过主题覆盖纳入同一套规范。
- 页面采用清晰的壳层、页面和业务组件边界，避免继续把页面样式堆在单个视图文件中。
- 新增流程可以演示，但明确不伪造真实 AI 分析结果或后端持久化。

## 应用壳层

重构 `App.vue` 和全局样式，形成以下结构：

```text
AppShell
├── TopHeader
├── SideNavigation
└── MainViewport
    └── RouterView
```

顶部区域保留 `DocReview AI` 品牌、一级导航、通知和帮助入口。侧边导航承载“新建分析”“当前批次”“最近文档”“星标条款”以及现有功能入口；当前路由通过蓝色激活状态体现。移动端侧导航收敛为顶部菜单或抽屉式区域，主内容不产生横向滚动。

现有路由的功能保持不变：`/`、`/docs`、`/history`、`/favorites`、`/detail/:id?` 和 `/docs/:id` 继续可访问，只迁移到新的壳层和视觉令牌下。

## 新增审查流程

新增独立路由：

| 路由 | 页面 | 核心内容 |
| --- | --- | --- |
| `/review/upload` | 文档上传 | 拖拽上传区、文件队列、批次属性、OCR 开关、额度卡片、AI 洞察卡片 |
| `/review/templates` | 范本选择 | 范本分类筛选、搜索、范本卡片、选中状态、文档洞察、匹配度 |
| `/review/rules` | 条款设置 | 财务与支付、合规与运营、模型微调、规则启停、配置预览 |
| `/review/console` | 智能审查 | 文档阅读区、缩放/打印工具、风险统计、风险卡片、处理动作 |

四页共享一个步骤条组件。步骤状态分为已完成、当前和未开始；上一步和下一步按照当前步骤更新本地流程状态。首次进入 `/review/upload` 时初始化一组稳定的演示数据，刷新页面不要求后端数据。

### 审查问答助手

智能审查页右侧使用 `审查发现` 和 `问答助手` 两个 Tab。`审查发现` 保留风险统计、核心风险、审批和导出操作；`问答助手` 展示当前选中风险的上下文、推荐问题、消息记录与输入框。问答使用确定性的本地演示回答，不调用现有 `/api/chat` 或其它后端接口。切换风险后，助手上下文随之更新；移动端保持同一 Tab 结构并纵向排列。

## 状态与数据流

新增独立的 Pinia review store，状态至少包含：

- 当前步骤。
- 本地演示文件列表及上传进度状态。
- 当前选中的范本。
- 分组条款的启用状态。
- 灵敏度、分析模型和标记逻辑。
- 当前风险列表及审批状态。

组件只通过 store 的动作修改流程状态。演示上传、范本选择、规则切换、灵敏度调整和开始分析使用本地同步动作或短暂的前端 loading 状态。不得调用 `/api/docs`、`/api/chat`、历史或收藏接口。现有页面继续使用现有 API 模块，不与 review store 互相依赖。

## 组件边界

优先抽取以下可复用组件：

- `AppShell`：全局布局与响应式壳层。
- `TopHeader`：品牌、主导航和工具入口。
- `SideNavigation`：工作台导航和当前项状态。
- `ReviewStepper`：四步状态条。
- `ReviewFooter`：上一步、下一步和流程状态提示。
- `UploadQueue`：演示文件队列与进度状态。
- `TemplateCard`：范本信息与选中态。
- `ClauseCard`：规则启停、标签和配置入口。
- `InsightPanel`：文档洞察、匹配度和风险摘要。
- `RiskCard`：风险等级、条款位置和解释内容。
- `ReviewAssistant`：选中风险上下文、推荐问题、消息列表和本地演示问答输入。

只在至少两个页面共享时抽取组件；单页布局保留在对应 view 内，避免为演示内容建立过度抽象。

## 视觉令牌

将原型中的视觉变量整理为 CSS 自定义属性，包括：

- 页面背景、表面层级、表面容器层级。
- 主文字、次文字、边框和禁用态颜色。
- 主操作蓝色及其浅色容器。
- 成功、警告、危险和信息状态色。
- 4px、8px 和 12px 的组件圆角层级。
- 4px 基础间距和 8pt 递进布局间距。
- 标题、正文和标签字号/行高。

全局样式同时处理 Element Plus 的按钮、输入框、选择器、表格、标签、消息和弹窗，使现有功能页与原型页在同一视觉语言下工作。禁止在新页面引入 Tailwind CDN 或依赖远程图片/字体才能正常渲染。

## 响应式与可访问性

- 桌面端使用左侧固定导航、主内容区和需要时显示的右侧洞察面板。
- 平板端收窄导航并将三列内容压缩为主内容加可折叠洞察区域。
- 移动端将侧栏、洞察和底部操作纵向堆叠，按钮文字不溢出，表格和长文档内容可在自身区域横向滚动。
- 交互控件使用语义化按钮、输入和复选框；图标按钮提供 `aria-label` 或可见 tooltip。
- 保留键盘焦点样式，文本与背景保持可读对比度，并遵守 `prefers-reduced-motion`。

## 错误与边界状态

原有功能页继续展示 API 加载失败、空列表、上传失败和删除确认状态。新增原型页至少覆盖：空文件队列、文件处理中、范本未选择、无启用规则、分析进行中、分析完成、风险为空和审批完成。演示状态必须有明确的视觉反馈，但不显示“已完成真实分析”之类会误导用户的文案。

## 验收标准

1. 现有所有路由仍可进入，原有接口调用、表格操作、问答流式输出和文档预览行为没有回归。
2. 四个新增 review 路由可通过导航和步骤条互相切换，流程状态连续且返回/前进符合当前步骤。
3. 新增页面能独立完成文件队列展示、范本选择、规则启停、参数调整和模拟分析结果展示。
4. 原型中的全局壳层、颜色、字体层级、边框、圆角、间距、步骤条、右侧洞察和风险卡片风格在现有页与新增页中保持一致。
5. `npm run build` 通过；在桌面、平板和移动视口检查无明显溢出、遮挡或不可操作控件。
6. 代码中没有新增远程 Tailwind CDN、远程字体或原型静态 HTML 的直接嵌套依赖。
